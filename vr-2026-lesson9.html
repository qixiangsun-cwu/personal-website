一

抓得住吗：attach() 与"最近的那一个"

案例 02 的抓取规则：0.45 m 内，挑最近的那一块碎片——"最近"是规则，不是"我想要"

抓取这个动作，很多人以为是一大段代码。其实就是一行 attach。真正需要你决定的只有一件事：手伸到多近，才算抓得住？

一、抓取的动作与触发器

  • 动作在 grab(obj, holder) 里，核心一行是 holder.attach(obj)——把物体挂到控制器上；
  • 触发它的是 squeezestart（握持键被按下）——不是扳机；
  • 案例 02 的规则：在 0.45 m 内挑最近的那一块碎片。
var best = null, bd = 0.45;          // ← 抓取距离
for (每块碎片 o) {
  var d = 控制器 到 o 的距离;
  if (d < bd && !o.placed) { bd = d; best = o; }   // 越近越优先
}
if (best) grab(best, c);
实现口径 1：抓取 = 就近取最近的一个，不是一个范围。所以两块碎片叠在一起时，你抓到的可能不是你想抓的那块——"最近"是规则，不是"我想要"。

二、★ 现场改 bd（3 分钟）

改成现象用户的感受
0.15抓不到——手就在碎片上，按握持键没反应"这游戏坏了"
1.5隔着半间房，碎片自己飞过来"这也太简单了"
太小抓不到，太大乱抓。这个数不是你"想"出来的，是你"调"出来的。案例 02 选 0.45，是它的选择，不是标准答案。
二

放得对吗：放置判定 = 距离阈值 + 吸附槽

松手（squeezeend）调 release(obj)；它里面没有"放错了"这个分支，只有一件事：量一下距离

var p  = obj.getWorldPosition();         // 碎片当前在哪
var fp = muralFrame.getWorldPosition();  // 壁画框在哪
if (p.distanceTo(fp) < 1.6 && !f.placed) {
    // 吸附到对应凹槽
    var slotX = -0.95 + f.idx * 0.95;
    obj.position.set(fp.x + slotX, fp.y, fp.z + 0.16);
    placeFragment(f);
}

两个数决定了一切：1.6 m 是"算不算放到框上"的阈值；slotX 是"吸到哪个槽"。

一、★ 现场改 1.6（3 分钟）

改成现象一句话
0.5太远放不进——明明站在框前面，松手还是掉地上阈值是"手感"，不是"正确值"；你要为你的场景调一个数
4.0太近误触发——在门口一松手，碎片自己飞过去吸上

二、吸附槽：为什么"放对了"还要再看一次代码

案例 02 的槽位是按碎片索引固定的：slotX = -0.95 + f.idx * 0.95——第 0 块 → −0.95，第 1 块 → 0，第 2 块 → 0.95。也就是说：无论你先捡到哪一块，它都只会去自己固定的那个位置。

写法 ① · 按索引固定（案例 02）

好处是不会抢位置；代价是顺序感弱——你随便捡哪块都行，顺序不对也能拼对。

写法 ② · 自动找最近的空槽

听起来更聪明，但你要多想一件事：两块碎片同时靠近同一个空槽的时候，谁赢？（这是案例 02 布置的作业方向）

实现口径 2 与 3：放置判定 = 距离阈值，不是一个"放对了"的 flag；只要落在阈值内，就自动吸到槽位。两种写法都对，但你得知道你选了哪一种，以及代价是什么。

⚑ 要让学生自己看出来的一件事：release() 里没有"放错了"这个分支——阈值内就吸附，阈值外就掉在原地。"放错"这件事在你的作品里到底发生了没有？

三

点得到吗：UV 命中 3D 密码键盘

进了沉浸模式，网页的 DOM 面板不渲染——你在 HTML 里写的 <button> 在头显里根本没存在过

先记住这个坑：进入沉浸模式后，浏览器的网页覆盖层不渲染。所以把按钮/面板写成页面的 <div> 或右上角 HUD，戴上头显一定看不见、也点不到。按键必须是场景里的一个物件。

一、按键是画在 canvas 上、贴到一块平面上的

canvas 384 × 512  →  THREE.CanvasTexture  →  PlaneGeometry(0.62, 0.82)  →  贴到墙上
var labels = ['1','2','3','4','5','6','7','8','9','C','0','OK'];
kp.keys.push({ id: labels[i], x: 24 + col*116, y: 150 + row*90, w:100, h:76 });

命中靠 uv：射线打到平面的哪一点 → 换算成 canvas 的像素坐标 → 落在哪个键的矩形里 → 就是按了哪个键。这就叫 UV 命中。

"改布局 = 改两个数组，不用重新建模。"这就是"逻辑全部暴露"的好处——这正是这个案例值得当教材的原因。

三、密码：错了只清空，不锁死

function keypadPress(id){
  if (id === 'C') { keypad.display = ''; }              // 清除键
  else if (id === 'OK') {
    if (S.step !== 3)                  toast('密码锁还没通电');   // 顺序门
    else if (keypad.display === CODE)  openDoor();                // 对 → 开门
    else { toast('密码错误'); keypad.display = ''; }              // 错 → 只清空
  } else { if (keypad.display.length < 4) keypad.display += id; } // 最多 4 位
}
  • 密码：var CODE = '3719'——它是星象提示给出的，不是让用户猜的；
  • 错的处理：清空输入框 + 提示"密码错误" + 音效。没有尝试次数限制、没有冷却、没有锁死；
  • 输入上限 4 位：display.length < 4——一个很便宜的防误触，挡住"用户一直按一直按"。
为什么不锁死？因为这是一个体验作品，不是银行 App。用户输错了，你的目标是让他再试一次，不是让他记住教训。
四

顺序校验：S.step 与"失败有代价但不惩罚"

什么叫顺序？就是你没做完第一步，第二步不认你

案例 02 用一个对象 S 装着全部状态，其中 step 是唯一的裁判：

S.step状态谁能推进它
0找碎片3 块碎片全部放置完成 → 进 2
2点星S.starProgress 满 4 → 进 3
3输密码密码正确 → 进 4（门开）
4通关——

这就是最小成本的顺序校验：每一个动作入口，先问一句"现在轮到你了没有"。

  • clickStar() 的第一行就是这道门：if (S.step !== 2) { toast('先找齐壁画碎片'); return false; }
  • keypadPress() 也一样：if (S.step !== 3) { toast('密码锁还没通电'); }

一、⚑ 这一屏最值得抄下来的一段

function clickStar(st){
  if (S.step !== 2) { toast('先找齐壁画碎片'); return false; }   // 门
  if (st.lit)       { toast('这颗星已点亮');   return false; }   // 已点过
  var expectIdx = STAR_ORDER[S.starProgress.length];            // 该点哪一颗
  if (st.idx !== expectIdx) {
      for (全部星) { 熄灭、order = -1; }        // ← 代价：全部熄灭
      S.starProgress = [];                      // ← 代价：进度清零
      toast('顺序不对，星辰归位重来');
      return false;                             // ← 但：没有任何锁死
  }
  ...
}

代价是什么

进度清零、四颗星全部熄灭、有音效与提示——这足够让用户知道他做错了。

不惩罚是什么

不扣时间 · 不锁死 · 不用刷新页面——立刻可以重来。这保证他不会放弃你的作品。

正确顺序（案例 02）：STAR_ORDER = [2, 0, 3, 1]，星名见 names = ['角','亢','氐','房'] → 也就是 氐 → 角 → 房 → 亢。

二、★ 演示：错序 → 复位 → 接着玩

用控制台直接调 Dunhuang.clickStar(Dunhuang.stars[0])，故意点错一颗，观察三件事：

  1. 已亮的星全部熄灭；
  2. 提示"顺序不对，星辰归位重来"；
  3. 再点正确的那颗，仍然能推进。
这三条合起来才是完整的"失败处理"。少任何一条，用户体验就掉一档：少了复位，用户可以乱点通关；少了提示，用户不知道为什么失败；锁死了，用户直接退出。
顺手一个调试技巧：这些函数挂在一个叫 Dunhuang 的对象上，控制台能直接调——Dunhuang.keypadPress('OK')、Dunhuang.clickStar(Dunhuang.stars[2])。你们自己的作品也应该留一个能从控制台推进状态的入口，调试能省一半时间。
实现口径 4 与 5：顺序校验必须有"复位"这一半；失败有代价但不惩罚——点错星只是重来，密码输错只是清空，可以立刻重输。

三、⚑ 谜题设计：线性，但每一步都不一样

步骤谜题交互方式状态推进
①找齐 3 块壁画碎片直接抓取（握持键）＋ 走到壁画框旁松手S.fragments[i] = true
②壁画拼合无操作（自动过场 / 提示）S.step: 0 → 2
③按顺序点亮 4 颗星射线点击 + 顺序校验S.starProgress 满 4 → step 3
④石门 4 位密码3D UI 键盘（UV 命中）正确 → 门开 → 通关

⚑ 四步，四种交互——这就是"线性但不枯燥"的做法。反例（要让学生自己认出来）：如果四步全是"点一个按钮"，这就不叫谜题链，叫四个进度条。

四、提示要分层：giveHint() 按 step 给不同粒度

同一个"提示"按钮，在三个步骤给三种不同的话：找碎片（step 0）→ 给位置；点星（step 2）→ 给下一颗是哪一颗；密码（step 3）→ 直接给密码。

提示是难度的调节旋钮，不是一句话。找碎片是空间搜索，最费时间；密码只是记忆力，卡在那里没有任何意义。⚑ 提问：你的作品里，"提示"现在给了什么？（很多人根本没写提示。）
五

谁都点得到：人因与可访问性三件套

三个键，全部由共享 XR 工程内核提供——你的作品只要接了同一个内核，这三个键自动就有；但"自动就有"只到面板这一层

一、先把默认假设拆开：它排除了谁

你的作品现在假设用户：站着 · 两只手 · 两个能用的手柄 · 眼睛正常 · 不戴眼镜也行 · 不觉得晕。把这条假设拆开：

假设谁被排除了
站着 / 能站轮椅使用者、久坐不适的人、空间不够的人
两只手都在单臂用户、临时空不出手的人（拿着一支笔、拄着拐）
右利手左利手（约十分之一的人）——40 人的班，四五个
双手柄都在、都有电手柄漂移 / 没电 / 没配对的人
手持控制器动作受限用户——手抬不起来、抖动、抓握无力
能看清小字低视力用户
这不是道德课。"约十分之一是左利手"、"有人暂时腾不出手"——这些是产品问题。一个作品如果只有一种输入方式，它就只有一个很窄的用户群。

二、三个键的真实参数（照抄，不要靠记忆）

键功能真实参数现场要看见什么
Shift+P 坐姿 / 站立 坐姿时工程面板与案例自有 UI 一起下沉 0.45 m、下倾 0.18 rad 站着很舒服、抬手就能点的面板，坐下就够不着——下沉之后坐着也能点到最下面一排键
Shift+H 惯用手与单手 循环 双手 → 单手（自动）→ 仅右手 → 仅左手 → 双手；单手模式下只接受主手的扳机 / 抓握 切到"仅左手"后用右手去点——没有任何反应，右手突然变成了摆设
Shift+G 注视停留点击 视线中心射线命中 UI，停留 1.2 s 即触发；命中处有注视准星，命中时收缩并变金，移开就重置、同一目标不重复触发（内核参数 gazeMs = 1200） 不用手柄，用眼睛点完整块密码键盘（包括最后按 OK 开门）

三、注册与委托：两个必须记住的词

XRCore.ui([keypad.panel]);   /* 把"我自己做的面板"登记给内核，坐姿时才一起下沉 */

XRCore.uiHit(function(rc){   /* 把"我的面板有没有被打中"委托给内核的注视计时器 */
  ...
  return { id:'xxx', fire:function(){}, dist:hit.distance };
});

不登记会怎样

你在内核之外自己做了一块面板，不登记，坐姿时它就不动——这正好是你们接下来改自己作品时会踩的坑。

为什么要委托

因为内核不会自己认识你的面板。你不告诉它，它就只会算工程面板那几块。

一个很细但很关键的反馈设计：准星命中时收缩并变金——这就是进度条；眼睛移开进度重置；同一个目标不重复触发，所以你不用怕"看多了一眼又点一次"。

四、本段的当堂动手（10 分钟）

  1. 打开案例 02，依次按 Shift+P → Shift+H（循环到"仅左手"）→ Shift+G；

六

一条通道铺到一半：本课的高潮

⚑ 结论留白，让学生自己说出来——教师说的话不超过 10 句，动作要慢，问题写在屏上不要马上回答

现场切到 Shift+G 注视模式，放慢动作演四步：
  1. 同一个密码键盘：手柄射线点得动；切到 Shift+G，用注视也点得动（停留 1.2 s，准星收缩变金），连按 OK 开门都可以；
  2. 接着去点星星：注视模式下点不动——停 1.2 秒、再停 2 秒，都没反应；
  3. 再去抓一块壁画碎片：注视模式下也抓不了——停多久都行，抓不了；
  4. 停下来，问全班一句（写在屏上，不要马上回答）：

"同一个作品里，为什么有些东西不用手柄也能点，有些东西死活点不动？"

教师注意（这一段最关键）：不要自己说出答案。等 2—3 个学生说完，再确认他们的说法。学生的答案应该指向下面这三句。

一、把刚才看到的东西列成一张表

元素类型免手柄能不能用为什么
工程面板UI能内核的注视计时器直接管
密码键盘（案例自有）UI能案例用 XRCore.uiHit() 委托给内核
四颗星场景实体不能判定走手柄射线命中（clickStar）
壁画碎片场景实体不能抓取绑在 squeezestart（握持键）上

两张"能"、三张"不能"，差别在哪儿？——结论这一行让学生说出来，教师再写上去：
"面板可免手柄，场景实体仍需手部输入。"
这不是案例的 bug，是真实产品里最常见的可访问性问题：一条替代通道铺到了一半，就以为铺完了。它在真实产品里天天发生——因为做的人有手柄，试的人也有手柄。

二、⚑ 该不该替？——取舍清单

想替代的动作替代方案代价
点星注视停留 1.2 s4 颗星 × 1.2 s ≈ 5 s 纯等待，节奏垮掉；顺序谜题变成"耐心测试"

"说出来" = 写进 README（这就是诚实）；"不说" = 骗人（用户以为你支持了，戴上头显才发现不行）。
照这个句式写，不要写成"支持免手柄"："本作品的可访问性覆盖范围：面板可免手柄；场景实体的抓取与选择仍需手柄。"

三、下课前的三句话

  1. 本课命题：交互的难点不在"能不能点"，在"点不到时怎么办"；
  2. 可访问性的诚实口径：面板可免手柄，场景实体仍需手部输入——能替代的替代，不能替代的要说出来；
  3. 接下来 65 分钟的顺序不能颠倒：先改（在电脑上打通主流程、连走两遍、控制台无报错）→ 再补（至少补一条免手柄通路，写下它覆盖到哪一步、覆盖不到哪一步）→ 最后戴（戴上头显走完整流程，抄用时 / 记卡点 / 报退出路）。
所有人在戴上头显之前，先把代码改完。不许一边改一边戴——那样一个人会占住一台头显一整段时间。

二、三条通路：课前选定一条，课上只教那一条

通路怎么走依赖适合
① USB + adb reverse（最稳）数据线连头显（开发者模式 + 允许 USB 调试）→ 笔记本执行 adb reverse tcp:8080 tcp:8080 → 头显浏览器打开 http://127.0.0.1:8080/一根数据线。完全不经过网络教室网络差；一插就通，天生安全上下文，不用加白名单
② 局域网 + 白名单笔记本起服务（serve.bat，零依赖）→ 头显浏览器打开 chrome://flags/#unsafely-treat-insecure-origin-as-secure，把 http://电脑IP:8080 填进去并 Enabled → 重启浏览器头显与笔记本同一网段、网络不隔离不插线、反复调试
③ 站点 HTTPS把作品放到课程站点的学生作品目录，头显直接打开 https 链接需要先把文件放上站点收作业与互相看
⚠️ 通路 ② 的三个坑：① 电脑 IP 一变就要重填；② 校园网 / 手机热点可能开「客户端隔离」，两台机器根本连不上，只能走 ①；③ 第一次运行 serve.bat 时 Windows 弹防火墙询问，必须点"允许"。
不要课上临时试第二条。40 台设备一起等一个没验证过的功能，是最容易把课拖垮的场面。
口诀（第 5 次课已确立，全程沿用）：先怀疑环境，再怀疑代码。"进入 VR"只在安全上下文里可用——https: / http://localhost / http://127.0.0.1 算；你电脑的局域网 IP（http://192.168.x.x）不算。用局域网 IP 打开时看不到「进入 VR」按钮、控制台里 navigator.xr 是 undefined——那不是学生的代码写错了，是环境不满足。这是本节课第一大故障源。

六、为什么这节课要花 65 分钟在验证上

"你今天做的所有事情，都能在你的电脑上看到结果。但有四件事只有戴上头显才知道：
① 你的东西在离眼睛十厘米的地方，看着是不是太大或太小；
② 你的手柄真的能抓住你要抓的东西吗；
③ 走完一整套要多久——这个数你在电脑上永远掐不准；
④ 你能不能退出去。
前三条决定你的作品好不好用。第四条决定你的作品算不算做完了。"

达标线与评价量规

全部课内完成，不卡时间；做不完登记后到实验室补做。今天的产出是三样东西，不是一张好看的截图

一、本节达标五条（缺一条不算过）

  1. 路子通：从入口到通关能连走两遍，控制台无报错；
  2. 放得对：抓取与放置各有一个说得出数值的判定（阈值 / 槽位）；
  3. 不锁死：顺序做错或密码输错之后，能立刻重来，不需要刷新页面；
  4. 能戴能退：头显里走完主流程，三条退出路至少试通一条并报出用时；
  5. 说得出边界：能回答"我的免手柄通路覆盖到哪一步、覆盖不到哪一步"。
两条硬门槛：A 主流程可玩 且 C 真机验证记录（含退出路）。路径不通或退不出去的，不进入下面的量规打分。

二、本节量规（五维，当场判达标用；与期末量规同源）

维度权重看什么
主流程完整30%入口→通关可重复、无报错、失败可恢复
交互实现25%抓取（attach()）· 放置判定（阈值 + 槽位）· UV 命中 3D UI · 顺序校验（S.step）
人因与可访问性20%三件套测过几条；免手柄通路覆盖边界说清楚；取舍理由
舒适与退出15%三条退出路至少一条、报出用时；默认传送 + Snap
诚实与文档10%README 写明已知简化与覆盖不到的地方；不确定信息标 【待补充】
保留"可访问性"为必评维度——它在期末量规里已并入「交互与人因 20 分」，不再作为加分项。这条改动的原因就是第 9 次课把它教成了硬要求。

三、任何情况下都不降的三条

  1. 达标线本身；
  2. 改动必须有依据——不能瞎填阈值，你得说得出"为什么是 0.45 / 1.6"；
  3. 记录表上的数字必须和页面 HUD 对得上——编数据比做不出来更严重。

一、八句话速查

主题要记住的
本课命题交互的难点不在"能不能点"，在"点不到时怎么办"
抓取attach() 一行挂上手；规则是0.45 m 内取最近的一个，不是一个范围
放置判定距离阈值 + 吸附槽：p.distanceTo(fp) < 1.6，吸到 slotX = −0.95 + idx×0.95
3D 键盘沉浸模式不渲染 DOM 按钮 → 按键是 canvas 贴图 + UV 命中；labels 与 kp.keys 共用 384 × 512 坐标系
密码var CODE = '3719'；错了只清空、不锁死；最多 4 位
顺序校验S.step 是唯一裁判；每个动作入口先问"现在轮到你了没有"
失败的设计失败有代价但不惩罚——代价是重来，不惩罚是不扣时间 · 不锁死 · 不用刷新
可访问性边界面板可免手柄，场景实体仍需手部输入；能替代的替代，不能替代的要说出来

键参数
Shift+P坐姿：下沉 0.45 m、下倾 0.18 rad；自有面板要先 XRCore.ui([面板]) 登记

三、上机五句话

  1. 先怀疑环境，再怀疑代码——看不到「进入 VR」按钮时，先看是不是安全上下文；
  2. 进 VR 必须人手点一次，这是规范要求，装成应用也一样；
  3. 先在电脑上改完，再戴头显——不许一边改一边戴；
  4. 退出有三条路：注视/射线点按钮 / 长按握把 2 秒 / 系统键。至少试通一条并报出用时；
  5. 记录表上的数字必须和页面 HUD 对得上——编数据比做不出来更严重。

M3 主流程可玩：硬门槛

一句话口径（板书就写这一句）：路子不通、或退不出去的作品，画面再好看也不算完成。

M3 是 11-11 第 9 次课的交件，卡住谁不能往下走——不过此关，作品不算完成。判定只看三样，不看画质、不看功能数量。

一、判定三项

#判定项过不过
A主流程可玩（硬门槛） 从入口到通关，能连走两遍，两遍结果一致；控制台无 JS 报错 中间有任何一步"只能靠老师帮你跳过"；或第一遍能过、第二遍状态残留导致过不去
B一条免手柄通路 至少一条不用手柄也能推进的通路存在，并且能说清它覆盖到哪一步、覆盖不到哪一步 完全依赖手柄；或声称"支持免手柄"但说不出覆盖边界——说不清 = 不过
C真机验证记录（硬门槛） 用时 / 卡点 / 退出路三样齐全，卡点写了具体在哪一步 三项缺一；或卡点栏写"没卡"/"很顺利"——无信息量 = 不过

二、三样之外的加分观察项（不计入是否过）

  • 抓取 / 放置的两个阈值自己调过并说出理由；
  • 顺序校验失败后能恢复（不锁死）；
  • 对"面板能免手柄、场景实体不能"这条边界有自己的处理或说明了取舍。

三、没过怎么办（不当场否定，给补做路径）

卡在哪补做安排
卡在 A 主流程第 10 次课课前 20 分钟一对一补；先查环境（三条通路），再查代码
卡在 B 免手柄通路允许降级为"键盘快捷键通路"（PC 端可完成主流程 + 至少一处 VR 内免手柄），但必须在 README 写明取舍
卡在 C 真机记录课后到实验室补做并补填【表 C】；不占用第 10 次课的 M4 时间
不减的底线：A 与 C。免手柄通路允许按上面的方式降级，但"能退得出去"没有降级选项。
