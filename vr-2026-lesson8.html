本课导览：给一堆“能做的事”装一个目标

上次课你手上有一堆能做的事——能抓、能点、能传送。但能做的事多，不等于有一件作品

第 7 次课（10-21）结束时，每个人手上有一个个人交互测试台：≥3 种交互 + 1 个 3D 面板按钮，PC 与 VR 两端都能完成；当晚还交了一份 M1 选题一页纸（主题 / 为什么必须 VR / 目标用户 / 核心交互 / 技术点 / 跑不动时的降级方案）。

那是一堆零件。这一课要做的事只有一件：给这些“能做的事”装一个目标——让它有“开始 / 进行中 / 完成了”。这个“目标”落到代码里，就是今天讲的动线 + 状态机。

本课的一句话命题：没有目标的空间叫场景，有目标的空间才叫作品。
本课的产出是三样：① 动线图　② 状态机图　③「入口 → 第一个目标」能跑起来的截图或录屏——三样一起就是里程碑 M2（设计定稿），今晚交。

一

衔接与第一件事：空间叙事

用空间讲故事，不是用文字说明

一、与第 6 次课的衔接：从“一张图”到“有状态的图”

第 6 次课（10-14）你已经学过：作品是一张图（节点 + 边）——可达性、无死胡同、最远几步，而且全都能在电脑上算出来，不用戴头显。今天在这张图上再往前推一格。

第 6 次课的一张图今天：有状态的图
节点一个房间 / 一个全景一个房间 ＋ 到了这里要发生什么
边一条热点 / 一条通路一条通路 ＋ 走这条边要满足什么条件
查得出的毛病死胡同、不可达、绕远再加上：卡死 · 状态与 UI 不同步 · 提示与校验对不上
判断工具连通性体检状态机表（每个状态：进入条件 / 离开条件 / 驱动了什么）

一句话：图上的每个点，不只连着边，还挂着一句“到了这里要发生什么”。加了这句话，图就变成了有状态的图——也就是今天的全部内容。

二、什么叫“空间叙事”

用空间讲故事，不是用文字说明。右边那一列全部是“改空间”，不是“加文字”。
文字说明的做法空间叙事的做法
门口立一块牌子写“这是一间藏经洞”让洞越来越窄、光越来越少，走到尽头才看见经卷堆
弹一个浮层写“请注意左侧壁画”把唯一的暖光打在左侧那幅壁画上
字幕写“你已经接近目标了”让门缝里透出的光先于门本身出现在视野里
为什么强调这个：戴着头显的时候，你的文字面板很可能根本看不见。上一次课已经踩过这个坑——沉浸模式里网页浮层是不渲染的，所以你的名字要写成 3D 物件。同理，你的说明也要写进空间里。

三、案例 02 的空间：主窟和侧窟不是“两个房间”

打开案例 02 的 PC 视图，看这个洞窟——它其实是两间，中间一道石门。

空间代码里的名字与尺寸（案例 src 实读）作用
主窟ROOM = { x0:-6, x1:6, z0:-8, z1:6, h:3.6 }碎片、星象毯、陈设都在这里
侧窟（门后）ROOM2 = { x0:6.3, x1:12, z0:-3, z1:3, h:3.2 }门开之后才能进——藏经洞
门洞石门开在主窟东墙 x = 6 上，门楣上方留墙，主窟东墙上留出 2.6 m 高的洞两个空间的连接点，也是“目标达成”的物理化
主窟 = “通关前”，侧窟 = “通关后”。空间划分本身就是叙事。
它没有用任何文字告诉你“这里是主窟”“那边是藏经洞”，它就是让你过不去——门锁着、墙是实的。“过不去”这三个字，比任何提示牌都有效；叙事的效果，是玩家自己在空间里撞出来的。

四、空间叙事的三个可操作手段（案例 02 里都在）

手段做法案例 02 里在哪
① 尺度改空间的长宽高ROOM.h = 3.6（主窟）vs ROOM2.h = 3.2（侧窟）——低一点就更闷
② 光决定“谁被照亮”一盏 DirectionalLight 出阴影 + 一盏 HemisphereLight 打底；另有 4 盏油灯是自发光球体，不是光源
③ 陈设放什么、放哪儿经卷堆（北墙根）、陶罐（南墙角）、佛龛（西墙）、中央地毯与星象图

记住一句：这三件事都不需要新素材。案例 02 里一张图片文件都没有——所有贴图都是代码画出来的，这事在下面「五、拆 02 的洞窟」里细讲。

五、一个要纠正的直觉：“看起来有 4 盏灯” ≠ “真的开了 4 盏灯”

  • 案例 02 里 4 盏油灯是 emissive 自发光球体 + 一根挂钩——不参与光照计算、不投阴影；
  • 真正参与光照的只有 2 盏：HemisphereLight + DirectionalLight（案例自己记的口径是“1 平行光（1024 阴影）+ 1 半球光”）；
  • 每多一盏真光源，所有受光材质的计算量都要涨一遍。

那 4 盏油灯长得很亮，但它们是画上去的亮，不是照出来的亮。你能骗过眼睛，但骗不过帧率——第 10 次课回来算这笔账。

二

动线三问：答案是数出来的，不是感觉出来的

第 6 次课你已经在六房间的漫游器上练过一遍；今天不做新东西，只是把它套到你自己的选题上

① 进得去吗？（从入口能不能到每一处）
② 出得来吗？（每个点有没有出边）
③ 有没有超过 3 步？（最远几步）

三问里，第 2 问是杀人最多的一问——大多数人不是进不去，是出不来。

一、三种典型的“坏图”

坏在哪长什么样玩家的感受
死胡同进得去，没有出边“我是不是走错了？”——然后原地转圈
不可达有节点从入口连不进去“那个地方怎么去？”——然后放弃
绕远能到，但要转 5 步以上“怎么还没到？”——然后失去耐心

这三种毛病肉眼看不出来，但体检一秒就出来。最要命的地方是：它们在做的时候看不出来——你自己知道路怎么走，因为你脑子里有那张图，但玩家没有。所以：这几种毛病不用戴头显就能查出来，而且必须在做作品之前查。

二、★⚑ 现场演示：把“最远几步”数出来

打开第 6 次课用过的 《漫游路线与连通性检查器》 与 《从入口走几步》：

  1. 连成一张图 → 体检三项全绿；
  2. 点预设「故意做个死胡同」→ 看它变红（例如删掉“卧室 → 餐厅”这条边，右边就读出“死胡同 1 个”）；
  3. 点「从入口出发」→ 看它一层一层点亮：第 1 步能到谁、第 2 步能到谁。
⚑ 现在请你自己回答：你选题里，从入口到最远的那个地方，几步？（停 20 秒，请 2 名同学报数）
“最远几步”这个数不是估的，就是这么一层一层数出来的——报不出来的人，今天工作室第一件事就是把这张图连出来。

本屏最后落到学生自己的选题上：把你的选题当成一张图，先在纸上连出来。

三、动线图要回答的四个问题

#问题记在哪
①节点有哪几个？（≥3 个，含“入口”）节点名
②每个节点连到谁？边
③每个节点几步可达？（从入口算）步数
④每个节点有没有出边？有 / 无

就这四个问题，全答完，你的图就合格了。注意第 4 问——这一栏填“无”的那个节点，就是你的死胡同。

三

状态机集中在一个 S 对象

动线图是地图，状态机是剧本——地图告诉你“能去哪儿”，剧本告诉你“去了之后世界会变什么样”

一、从“图”到“有状态的图”

你画的动线图回答的是“能去哪儿”，它回答不了“到了那儿，然后呢？”

只有动线动线 + 状态
走到壁画前走到壁画前 → 碎片齐了 → 自动拼合 → 亮起星象
门在那儿门在那儿 → 密码对了 → 门才开

一件作品两个都要有。

二、案例 02 的谜题链：4 步，每步交互方式都不同

步骤谜题交互方式状态推进
①找齐 3 块壁画碎片直接抓取（握持键）+ 走到壁画框旁松手放置S.fragments[i] = true
②壁画拼合（自动）无操作，过场提示S.step: 0 → 2
③按顺序点亮 4 颗星射线点击；顺序错则全部熄灭重来S.starProgress 满 4 → step 3
④石门 4 位密码3D UI 键盘（射线点按键 UV 命中）正确 → 门开 → 通关

线性，但每步交互不同

抓取 → 自动过场 → 点星 → 输密码。四步、四种完全不同的交互方式——避免“全程只点一个按钮”的枯燥。别让玩家从头到尾只干一件事。

失败有代价但不惩罚

点错星只是重来，不扣时间、不锁死。“失败有代价，但不惩罚”——这条抄下来，今天做设计就能用。

状态机集中在一个 S 对象

S.step 驱动 UI、提示、音效、门的开关。这是可维护的关键，也是下面全部内容的中心。

三、一切都在一个 S 里（案例源码第 90—103 行）

var CODE = '3719';               // 星象提示的密码
var STAR_ORDER = [2, 0, 3, 1];   // 正确点星顺序（对应 4 颗星索引）
var S = {
  step: 0,            // 0 收集碎片  1 拼合(自动过渡)  2 点星  3 输密码  4 通关
  fragments: [false,false,false],
  starProgress: [],
  input: '',
  doorOpen: false,
  solved: false,
  hintsUsed: 0,
  time: 0
};
var STEP_NAMES = ['① 找齐 3 块壁画碎片', '② 壁画已拼合，查看星象', '③ 按顺序点亮 4 颗星',
                  '④ 在石门输入 4 位密码', '★ 通关'];
整个作品的“现在到哪一步了”，就是这一个对象。门开没开、碎片找了几个、点到第几颗星、通关了没有——全在这里。

上面那两行 CODE 与 STAR_ORDER 是常量（答案），下面这个 S 是变量（过程）。记住这个区分：答案不该变，过程天天变。把答案写进 S 里，是新手最容易犯的错。

四、S.step 一个数，驱动五件事

                        ┌─→  步骤面板 / UI（updateStepsUI）
                        │
                        ├─→  提示牌文案（drawKeypad 里的提示区）
   S.step  ────────────┼─→  提示系统（giveHint 按 step 给不同粒度）
                        │
                        ├─→  音效（clickStar / keypadPress 里的 beep）
                        │
                        └─→  门（openDoor 把 step 置 4）

左边只有一个东西：S.step；右边是五件事。这就是“集中”的意思：你改一个数，UI、提示、音效、门全都跟着变。

反面教材是什么？把“现在第几步”分别记在五个地方——面板里存一个 curStep、提示里存一个 hintStage、门自己再存一个 doorState……改了一个忘了另一个，就出了今天后半段要演的那种事故。

五、从外面能看到里面（达标线第 2 条）

案例 02 的做法（源码末行）：把状态与调试入口挂到 window.Dunhuang——

window.Dunhuang = { S: S, fragments: fragments, stars: stars, keypad: keypad, door: door, ... }

于是在控制台当场敲：

window.Dunhuang.S
// { step: 0, fragments: [false,false,false], starProgress: [], input: '',
//   doorOpen: false, solved: false, hintsUsed: 0, time: 0 }

意思是：不用读你的源码，我也能知道你作品现在走到哪一步了。三个好处：① 你自己调试方便；② 老师验收方便；③ 以后接数据、做成就系统都要靠它。

本课达标线第 2 条就是这个：你的状态必须能从外部查到——用你自己的名字，如 window.MyWork.S。课堂上会挨个到座位上敲一遍。

六、状态机图长什么样：每个状态一行，四个格子填满

状态进入条件离开条件驱动了什么
step 0 找碎片开始 / 重置碎片 3/3 归位碎片自发光、底座、提示文案、步骤面板
step 2 点星壁画拼合完成（从 0 直接跳到 2）四颗星按序点亮星的明暗、顺序提示、密码键盘是否通电
step 3 输密码四星归位键盘输入 = CODE密码键盘显示、OK 键是否可用
step 4 通关密码正确——（终态）门开动画、通关提示、用时
⚠️ 注意：step 1 是“过渡态”——案例 02 里拼合是自动完成的，所以 S.step 从 0 直接跳到 2（源码注释里也写着“1 拼合(自动过渡)”）。图上要如实画出来，别硬凑一个不存在的状态。画图要按代码的真相画，不要按你想象的画——图和代码对不上，图就没用。

七、状态机也会“得病”：三种典型病症

病症症状根因
卡死条件满足了，状态不推进状态转移那根线写错了
不同步状态变了，UI / 提示没变状态没集中，或者改了没刷新
对不上提示说的和校验要的不一致提示和校验读了不同的东西
这三种病症，都不报错、不崩溃，就是让你走不下去。它们最讨厌的地方是：代码没错，控制台干干净净，画面也没坏——就是……走不下去。下面两屏现场演给你们看，你们来判断这是哪一种病。
四

提示分层 giveHint()

提示不是“有”或“没有”，是“给多细”——读 S，不要存 S

一、一个函数，四个分支（案例源码）

function giveHint(){
  S.hintsUsed++;
  var msg = '';
  if(S.step === 0){
    var missing = [];
    for(var i=0;i<fragments.length;i++)
      if(!S.fragments[i]) missing.push(fragments[i].hint);
    msg = '还有碎片没找到：' + (missing.join('；') || '无');
  } else if(S.step === 2){
    var next = STAR_ORDER[S.starProgress.length];
    msg = '下一颗星：' + stars[next].name + '（' + ['左上','右上','左下','右下'][next] + '）';
  } else if(S.step === 3){
    msg = '密码是 ' + CODE;
  } else msg = '已经通关了';
  toast('提示：' + msg, 4200);
}

每个分支给你的粗细程度是不一样的：

  • 找碎片的时候，它只告诉你在哪个角落（“北墙根，经卷堆旁”）——说的是位置；
  • 点星的时候，它直接告诉你下一颗叫什么、在哪个方位——说的是答案；
  • 输密码的时候，它直接把密码念出来。

越往后越直白。这是故意的。

二、提示分层的两条规则

规则一：粒度跟着“玩家卡了多久”走

越往后越具体。前期给位置，中期给方向，后期给答案。

规则二：giveHint() 必须读 S.step，不许自己存状态

案例 02 的这个函数一行 S 都没改（只 S.hintsUsed++ 记了个数）——它完全靠 S.step 判断该说什么。

提示系统不该有自己的一套状态。如果 giveHint() 里自己存一个 hintStage，那就会出现后面现场改码演的那种事故——S.step 走到 3 了，hintStage 还停在 1，于是提示和画面完全脱节。读 S，不要存 S。

三、提示的两个副产品：它们本身就是数据

案例 02 记了两个数：S.hintsUsed（用了几次提示） 与 S.time（用时）。

谁用了 4 次提示才通关、谁一次没用——它们是你作品唯一能自己长出来的数据，也就是你作品的体检报告。第 11 次课的“体验数据导出”就靠这些。

两个副产品 = 第 10 次课（性能）与第 11 次课（数据）的伏笔。时间不够时，这一段是降级优先级里第一个可砍项（改成课后阅读本节的源码与两条规则）——但“状态机集中在一个 S 对象”与现场改码高潮不许砍。

一、断线 A（对应课件屏 22）：把“提示顺序”改错一处

把第 3 位换掉，其余不动：

// 原始（案例 README「五、源码改动入口」里的真入口）
var STAR_ORDER = [2, 0, 3, 1];   // 角 → 氐 → 房 → 亢

// 改错一处（示范用）：把第 3 位换掉
var STAR_ORDER = [2, 0, 1, 3];

改完会发生什么（照提示点，反而失败）：

谁在读 STAR_ORDER读的是它的什么改完之后
提示牌（drawKeypad 里的星象提示行）读名字：STAR_ORDER.map(i => stars[i].name)提示第三颗点 「房」
giveHint()（step === 2 分支）读名字 + 方位：stars[next].name同样告诉你点 「房」
clickStar() 校验读索引：STAR_ORDER[S.starProgress.length] 与 st.idx 比对第三颗必须是「氐」
结果：照着提示点 → 判“顺序不对，星辰归位重来” → 四颗星全灭。
原因：提示读的是名字，校验读的是索引——换掉的是“第三颗叫什么”，但位置上的那颗星没变。提示和校验，读了同一个数组的不同字段。
⚑ 这是三种病里的哪一种？等学生喊出来：“对不上”。这就是为什么反复强调：状态要集中、语义要单一。一个数组同时兼职“提示文案”和“校验依据”，改一处就两头不对。
（改回去：STAR_ORDER = [2, 0, 3, 1]）

改完会发生什么（全部走对，还是走不下去）：

你做了什么画面上的反应但……
找齐 3 块碎片、放进画框提示“壁画拼合完成”、步骤面板跳到第 3 行✅ 正常

没有报错、没有崩溃、控制台干干净净。整套交互看起来都对——就是走不下去。这就是“状态机没接上”。

三、让学生自己说出的那句话

“坏的不是画面，是状态机的那一根线。”

画面坏了你看得见，状态机坏了你看不见——它坏的方式往往不是崩溃，是“什么都没发生”。
这种 bug 最难查，因为你连报错都没有。

问法照这个顺序走：步骤面板跳行了吗？（没有）→ 再按 H，提示在说什么？（还在念下一颗星）→ 走到门口按 OK 呢？（“密码锁还没通电”）→ 谁能用一句话告诉我，坏在哪儿？（等学生说）

改完记得改回去（=== 4），或者直接用备份覆盖回来。

一、八句话速查

主题要记住的
本课命题没有目标的空间叫场景，有目标的空间才叫作品。
与第 6 次课的衔接从“作品是一张图（节点 + 边）”升级成有状态的图：节点还挂着“到了这里要发生什么”，边还挂着“走这条边要满足什么条件”
空间叙事用空间讲故事，不是用文字说明；三个手段是尺度 / 光 / 陈设，都不需要新素材
动线三问进得去吗？出得来吗？有没有超过 3 步？三种坏图：死胡同 / 不可达 / 绕远
有状态的图动线图是地图，状态机是剧本；地图说“能去哪儿”，剧本说“去了之后世界会变什么样”
状态集中一切在一个 S 对象里；S.step 一个数驱动 UI / 提示牌 / 提示系统 / 音效 / 门；常量（答案）与变量（过程）分开
三种病症卡死（状态转移那根线写错）· 不同步（状态没集中或改了没刷新）· 对不上（提示和校验读了不同的东西）
提示分层粒度跟着“玩家卡了多久”走：前期给位置、中期给方向、后期给答案；giveHint() 读 S，不存 S

事实与边界：数字有两个口径，可访问性只走到一半

这一节不掩盖任何一条——课堂上照这里说的念，不许把两个数混成一个

一、性能数字：README 值与审计值，如实并列

口径DrawCall三角面来源
README 值42 draw calls1.2 k 三角面案例 02 的 README_教学说明.md（记的是“接入 XR 工程面板前”的实测值）
审计值44124006_WebXR课堂案例\_标准与审计\标准_大四年级课程标准.md 的 verify.py 记录
课上一个说“README 值”、一个说“审计值”，不要混成一个数。顺带讲一句：同一件事，两次测量可以不一样。
还要明说：DrawCall / 三角面只是渲染规模指标，不代表帧率——真机瓶颈常在填充率与纹理带宽。不要把它当成“能跑 72Hz”。

二、可访问性的半成品状态：如实保留，留作讨论题

案例 02 的注视停留（Shift+G）只能点 3D 面板——包括完整的密码键盘，能一路点到 OK 开门。
但点星与抓碎片仍然需要手柄（射线 / 握持键）。

这是“面板支持了、场景物件没支持”的半成品状态。按案例 README 的写法，这条边界留作课堂讨论题，不掩盖：

  • 为什么会出现这种情况？
  • 如果你要做可访问性，你会先补哪一边、代价是什么？
这条边界下次课（11-11，第 9 次课）正式讲。下一课的人因与可访问性三件套是 Shift+P 坐姿（UI 下沉 0.45 m）· Shift+H 惯用手 / 单手 · Shift+G 注视停留 1.2 s。

三、案例 02 的验证状态（诚实说明）

  • 案例 02 的全部结论来自 headless Chrome + SwiftShader 软件渲染；帧率、眩晕感、手柄映射、会话进入均未真机验证。
  • 因此上课前一天必须真机跑一次 02（含进入与退出）；课堂演示以 PC 端为主，头显留到第 9 次课。
  • 涉及真实机构、校史、文物的具体信息，本课不编造，统一写占位。

动线图记录表：节点（房间 / 区域）｜ 连到谁（出边，逗号分隔）｜ 从入口几步可达 ｜ 有没有出边 ｜ 备注；入口那一行步数固定填 0。表下另有三个体检结论（能走到每一处吗 / 有没有死胡同 / 最远几步，要求 ≤3）。

状态机记录表：状态名 ｜ 进入条件 ｜ 离开条件 ｜ 驱动了什么（UI / 提示 / 音效 / 门 / 其他）；并回答三问——那个唯一的状态对象叫什么 / 里面有哪些字段 / 哪个字段是“现在走到哪一步”。

两个容易画错的地方：① 过渡态要如实画——案例 02 里 S.step 没有“1”这个停留状态（拼合是自动的，0 直接跳到 2），别硬凑一个不存在的状态；② 图和代码必须对得上，图上的每个箭头都要能指到一行代码。
