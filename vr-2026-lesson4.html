一、为什么这节课值得单独讲 WebXR

① 分发成本几乎为零

做 Unity 项目要经历"打包 → 安装 → 启动"；网页端只要一个链接。同学、家人、评委的浏览器都能直接打开，不需要装任何东西，也不经过应用商店审核。

② 迭代成本极低

改一行代码、刷新页面就是一次完整迭代，不必等构建与部署。做原型验证时，这条路线的时间成本通常是引擎路线的几分之一。

③ 它把第 3、4 章缝在一起

刷新率、分辨率、定位方式这些硬件指标，在浏览器里变成了可以现场读到的数字：FPS 面板、像素比、WebXR 的参考空间。硬件不再是纸上的参数。

一

WebXR 是什么：把 VR 放进浏览器

浏览器不再只是"看网页的软件"，它可以是一台 VR 运行时

1.1 一句话定义

WebXR Device API 是由 W3C 制定的浏览器标准接口，让网页代码直接驱动头显、手柄与空间追踪能力。它取代了早期的 WebVR（只做 VR、接口零散），把 VR 与 AR 统一到同一套 API 之下。

这句话的真正含义是：做 VR 应用，不再是引擎的专利。一个 HTML 文件加上几百行 JavaScript，就能在头显里跑起来——这也是本讲要亲手验证的事。

1.2 七个必须记住的概念

概念写法 / 取值含义与用途
能力入口navigator.xr浏览器是否具备 XR 能力。它是 undefined，后面的一切都无从谈起
会话模式immersive-vr / immersive-ar / inline沉浸式 VR / 沉浸式 AR / 页面内嵌（不接管显示）
参考空间local-floor / bounded-floor / local / viewer世界原点定在哪里。local-floor 以用户脚下的地面为原点，最符合"站着的人"的直觉
输入源inputSources手柄、手势、眼动等输入设备，以及它们的姿态与按键
帧循环renderer.setAnimationLoop()进入 XR 后渲染节奏由头显接管，必须改用它
安全上下文HTTPS 或 localhostWebXR 的硬性前提，不满足时 navigator.xr 会被藏起来
会话生命周期requestSession() → session.end()进入与退出 VR；退出后要交还控制权给页面

1.3 最重要的一条工程约束：安全上下文

WebXR 只在"安全上下文"里可用：https://… 或 http://localhost（含 127.0.0.1）。
用 file:// 双击打开、或用局域网地址 http://192.168.x.x 访问时，浏览器会把 navigator.xr 直接藏起来 —— 这时你测出来"这个设备不支持 WebXR"，是一个假结论。

为什么浏览器要这么做？因为 VR 会读取头显与手柄的空间姿态，属于敏感能力，标准要求它必须运行在可验证来源的页面里。这条规则没有例外，也不看你的设备有多贵。它是本讲最容易误判、也最容易浪费半天时间的一个点。

第七节会给出三条绕行路线（HTTPS 托管、端口转发、浏览器白名单）。请记住排查顺序：先问"是不是安全上下文"，再问"设备支不支持"。

1.5 网页端路线能做什么、做不到什么

✅ 很合适

  • 展览、漫游、导览类场景（本讲就是）；
  • 课堂演示与快速原型：改一行、刷一下就能看；
  • 跨设备分发：PC 浏览器、头显浏览器、手机同一条链接；
  • 与网页生态打通：二维码、微信、课件页面直接嵌入；
  • 轻量交互：传送、抓取、面板 UI、开关与滑块。

⚠️ 代价高或不合适

  • 复杂实时全局光照、电影级写实美术（算力不够）；
  • 超大场景（GB 级模型与贴图，加载时间不可接受）；
  • 需要离线包、本地文件系统或设备专属能力的重型应用；
  • 对延迟与稳定性要求极高的竞技类内容；
  • 完全依赖某个厂商专属 SDK 的功能（网页端只能走标准 API）。

二

技术栈与最小可运行场景

30 行代码，把一个球体放进 VR —— 先跑通骨架，再谈故宫

2.1 三件套：页面、样式、逻辑

层技术在本项目里负责什么
页面层HTML画布容器、HUD 面板、加载进度、"进入 VR"按钮
样式层CSSHUD 排版、按钮状态、提示浮层
逻辑层JavaScript建场景、算几何、画贴图、处理输入、驱动 XR 会话
3D 库Three.js（r128，UMD 版）把 WebGL 的复杂细节封装成 Scene / Mesh / Material / Light

浏览器本身已经提供了两套底层能力：WebGL（画三角形）与 WebXR（接管头显）。但直接用原生 WebGL 画一座故宫，意味着你要自己写着色器、自己算矩阵、自己管理缓冲区。Three.js 的作用就是把这些收起来，让我们把精力放在"宫殿应该长什么样"，而不是"投影矩阵怎么乘"。

2.2 先说一个必须提前知道的坑：库的加载方式

<!-- ✅ 本项目采用：UMD 单文件，双击 file:// 也能加载 -->
<script src="./three.min.js"></script>

// ❌ ES Module 版：在 file:// 下会被浏览器的同源策略拦下
import * as THREE from 'three';

本项目用的是 Three.js r128 的 UMD 构建（单文件 603 KB），用普通 <script src> 引入。两者的区别直接影响调试体验：UMD 能在 file:// 下加载，ES Module 不能——这是"双击就能预览"和"必须先开服务器"的分界线。

但要再说一次：file:// 只能预览画面，进不了 VR。进 VR 仍然需要安全上下文。

2.3 七类核心对象

对象作用在本项目里对应什么
Scene场景根节点，所有物体的容器整座紫禁城
PerspectiveCamera观察者（投影方式与视锥）你的眼睛；进入 VR 后姿态由头显驱动
WebGLRenderer每帧把场景画出来输出到画布或头显的双眼视图
Mesh可渲染物体 = 几何体 + 材质一根柱子、一片瓦顶、一块台基
Group物体的分组容器一座单体建筑（太和殿、午门……）
Light光照1 盏平行光 + 1 盏半球光
Raycaster射线拾取，判断"指着谁"点击地面 / 扳机传送的落点判定

2.4 渲染循环：两行代码的差别

// 普通网页动画：浏览器按刷新率回调
requestAnimationFrame(tick);

// 进入 VR 之后：渲染节奏交给头显，必须改用这一行
renderer.setAnimationLoop(tick);
在 XR 会话里继续用 requestAnimationFrame，典型症状是戴上头显就黑屏或卡住：头显的合成器要求每个 XR 帧都提交画面，而这个节奏由 setAnimationLoop 保证。Three.js 会自动为左右眼各渲染一次，并把结果交给头显合成器。

2.5 最小可运行场景（完整 30 行）

<!DOCTYPE html>
<html><head><meta charset="utf-8"><style>body{margin:0;overflow:hidden}#vr{position:fixed;left:12px;bottom:12px}</style></head>
<body>
<button id="vr">进入 VR</button>
<script src="./three.min.js"></script>
<script>
  // 1) 三个基本对象
  var scene = new THREE.Scene();
  scene.background = new THREE.Color(0x9ec9f0);
  var camera = new THREE.PerspectiveCamera(70, innerWidth/innerHeight, 0.1, 2000);
  camera.position.set(0, 1.6, 4);            // 1.6 m ≈ 人眼高度
  var renderer = new THREE.WebGLRenderer({antialias:true});
  renderer.setSize(innerWidth, innerHeight);
  renderer.setPixelRatio(Math.min(devicePixelRatio, 1.5));
  document.body.appendChild(renderer.domElement);

  // 2) 一盏灯 + 一个物体
  scene.add(new THREE.HemisphereLight(0xbcd8f0, 0x6b5a44, 0.9));
  var ball = new THREE.Mesh(
    new THREE.SphereGeometry(0.6, 32, 24),
    new THREE.MeshStandardMaterial({color:0xb22222})
  );
  ball.position.y = 1.2;
  scene.add(ball);

  // 3) 让渲染器接管帧循环（XR 必需）
  renderer.xr.enabled = true;
  renderer.setAnimationLoop(function(){
    ball.rotation.y += 0.01;
    renderer.render(scene, camera);
  });

  // 4) 进入 VR
  var btn = document.getElementById('vr');
  if(!navigator.xr){ btn.disabled = true; btn.textContent = '当前浏览器不支持 WebXR'; }
  else navigator.xr.isSessionSupported('immersive-vr').then(function(ok){
    if(!ok){ btn.disabled = true; btn.textContent = '本设备不支持沉浸式 VR'; return; }
    btn.onclick = function(){
      navigator.xr.requestSession('immersive-vr', {optionalFeatures:['local-floor']})
        .then(function(s){ renderer.xr.setSession(s); })
        .catch(function(e){ btn.textContent = '启动失败：' + e.message; });
    };
  });
</script>
</body></html>

2.6 进入 VR 的四步

  1. 检测能力：navigator.xr 是否存在（不存在 = 浏览器或安全上下文不满足）；
  2. 检测会话模式：navigator.xr.isSessionSupported('immersive-vr')；
  3. 请求会话：navigator.xr.requestSession('immersive-vr', {optionalFeatures:[...]})；
  4. 交给渲染器：renderer.xr.setSession(session)。
optionalFeatures 与 requiredFeatures 的区别很关键：写进 requiredFeatures 的能力如果设备不支持，会话会直接失败；写进 optionalFeatures，设备有就用、没有就降级。本项目请求的是 local-floor（地面原点）、bounded-floor（安全边界）、hand-tracking（手势），全部写成可选——这样即使头显没有手势追踪，场景照样能进。

2.7 随堂实操 A（约 10 分钟）

  1. 把上面的最小场景存成 hello-webxr.html，与 three.min.js 放在同一目录；
  2. 双击打开（file://）——画面应该能出来，但按钮会显示"不支持 WebXR"。先亲眼看到这个"假结论"；
  3. 把 SphereGeometry 的半径从 0.6 改成 1.5，把材质颜色改成自己喜欢的颜色，刷新；
  4. 按 F12 打开控制台，确认没有红色报错。
这一步的目的不是"做出东西"，而是亲手确认两件事：① WebXR 的可用性受安全上下文控制；② 改一行代码、刷一下页面就是一次完整迭代——网页端路线快在哪里，你自己感受得到。
三

程序化生成故宫：几何

没有一砖一瓦的模型文件，宫殿是"算"出来的

3.1 为什么选择"用代码建模"

方案体积网络依赖可控性适合本讲吗
下载现成模型（素材库 / AI 生成）几十 MB ～ GB需要下载受精度与授权限制不适合：课堂网络不可控，版权也不清楚
建模软件自制（Blender）中等需要分发高不适合本次课：40 人在一节课里做不完
程序化生成（本讲）约 660 KB零请求，断网可用每个尺寸都是一个可调变量✓ 采用

程序化建模还有一个隐藏收益：它是"可解释"的。模型文件里的一根柱子是几万个顶点坐标；而程序里的一根柱子是 addPillar(x, z, y0, h, r)——想让它高一点，改一个数就行，还能顺便讲清"高多少算合理"。

3.2 先把坐标系定死

  • 1 个世界单位 = 1 米，与历史资料上的尺寸可以直接对话；
  • y 轴朝上；中轴线取 x = 0；本项目取 +z 为南、−z 为北（午门在南、三大殿在北）；
  • 每座建筑一个 Group：Group 只负责"整体落位"，内部构件一律用局部坐标，之后整体移动、旋转、复制都不会散架；
  • 玩家活动范围单独用一个常量圈住：{ wallX: 82, southZ: 170, northZ: −178 }。
单位先定，比例才不会乱。建模最常见的灾难不是"面太多"，而是"不知道自己用的是厘米还是米"——最后做出来的人比柱子高，或者柱子比宫殿还粗。

3.6 三个一定会踩的坑

  1. 梯形屋面不是三角形。庑殿顶的前后坡是梯形，需要 6 个顶点、6 组 UV；只按 3 个顶点写，屋面会缺一大块。
  2. 法线要自己算。手写几何体不会自动获得正确法线；法线错了，屋顶会"一块亮一块黑"，看起来像贴图坏了，其实是光照方向错了。
  3. UV 要按实际尺寸。贴图的重复次数应随构件的米数计算（repeat.set(宽/6, 高/4) 这类写法）。否则同一张瓦片贴图，在小屋上被拉长、在大殿上被压扁，砖缝大小对不上。

还有一个更"隐蔽"的坑写在 PART 6：把局部坐标当成世界坐标用。当物体带父容器（Group）时，它的坐标是局部的，合批前必须先换算到世界坐标，否则上千根柱子会整体错位。

4.1 为什么不用一张图片贴图

本项目的贴图不是图片文件，而是运行时用 Canvas 2D 画出来、再交给 GPU 的 CanvasTexture。四个好处：

4.3 材质复用：把纹理 clone 出来改重复次数

// 生纹理一次，改 repeat 复用；用 key 缓存，避免重复创建材质
var matCache = {};
function wallMat(w, h){
  var key = 'w' + (w|0) + '_' + (h|0);
  if(matCache[key]) return matCache[key];
  var t = tex.wallR.clone();                 // 克隆纹理，各自设置平铺次数
  t.needsUpdate = true;
  t.repeat.set(Math.max(1, w/6), Math.max(1, h/4));
  return (matCache[key] = new THREE.MeshStandardMaterial({map:t, roughness:0.9}));
}
为什么必须缓存？材质对象在渲染时对应着色器程序与提交批次。同样的墙面每出现一次就新建一个材质，会让 Draw Call 成倍膨胀——这正是 PART 5 要处理的问题。记住一条经验：能复用的材质就复用，能让纹理 repeat 解决的就别新建材质。

4.4 光照：两盏灯打完全场

  • 1 盏平行光（DirectionalLight）：模拟日光，负责明暗与投影；
  • 1 盏半球光（HemisphereLight）：模拟天光与环境补色，避免背光面死黑；
  • 没有实时点光源：夜间的灯笼与灯火不新增光源，只调材质的自发光强度。

阴影用一张 2048 的 PCFSoft 阴影贴图，正交阴影相机按中轴范围裁剪，并设置 bias / normalBias 抑制摩尔纹。

阴影范围是一个必须做的取舍。阴影贴图的分辨率被摊在整个阴影相机范围内：范围开得越大，单个像素覆盖的地面越大，阴影就越糊、越抖。开得太小，远处的建筑又投不出影子。所以正确做法是让阴影相机只包住视野中必须投影的部分（本项目取中轴一带约 ±210 m × 140～190 m），而不是无脑盖住全场。

4.5 雾、天空与昼夜

  • 雾（Fog 220 m → 780 m）：让远景自然淡出。它的作用不只是好看——可以用更近的渲染距离而不穿帮，等价于省算力；
  • 天空球：一个从内侧观察的球体，颜色随时间变化，同时作为雾色与整体色温的来源；
  • 昼夜插值：用一组时间变量在"白天 / 黄昏 / 夜晚"三套颜色之间平滑过渡，只改 uniform 与材质自发光强度，不重建几何与材质；
  • 默认取下午 15:00——斜阳下屋檐投影最长，立体感最好。
把"时间"做成一个可以滑动的变量，是这类场景性价比最高的一招：几行插值代码，换来一整套"晨昏四季"的可讲内容，而且几乎不增加渲染负担。

5.1 先算一笔帧预算

头显刷新率 72 Hz 意味着每帧只有约 13.9 ms（1000 ÷ 72）。这 13.9 ms 里要同时完成：CPU 逻辑与物理、Draw Call 提交、GPU 渲染、以及双眼画面的合成。移动头显用的是移动芯片级 GPU，没有独立显卡，也不能靠风扇长时间压散热。

把这句话和上节课的硬件内容连起来看：刷新率不是一个抽象的规格数字，它是一份必须按时交卷的时间预算。超了就掉帧，掉帧就眩晕——这是第 2 章讲过的 Motion-to-Photon 延迟在工程上的真实来源。

6.3 舒适度：为什么是"传送 + 分步转身"

为什么用传送，而不是连续行走

VR 里"人没动、画面在动"最容易引发不适：前庭系统感觉没动，视觉系统却报告在加速。瞬移把连续的加减速打断，是当前最稳的移动方案。本项目 VR 里保留的平滑行走也刻意压到 4.2 m/s，并只在"沿头朝向"这一个方向上生效。

为什么是 30° 一档，还要 350 ms 冷却

连续旋转同样容易晕。Snap turn 把转动切成 30° 一档，一档一档转；350 ms 冷却是为了防止摇杆轻微漂移被识别成连续输入，导致画面一直转个不停——这类"小概率但高频"的手感问题，靠参数调，不靠运气。

6.4 一个必须绕开的坑：不要在 VR 里每帧写相机姿态

// ❌ 错误：进入 XR 后，相机姿态由头显每帧写入，你写它 = 两边互相覆盖
camera.rotation.y += 30 * Math.PI / 180;

// ✅ 正确：旋转"玩家"这一层父节点，相机保持由头显驱动
player.rotation.y += 30 * Math.PI / 180;
症状很有欺骗性：画面抖动、视点漂移、转向失灵，甚至戴上头显后画面"粘"在脸上。原因是你和头显在抢同一个属性。正确做法是把玩家做成一个 Group（rig），所有转身、位移都作用在 rig 上；相机作为它的子节点，只负责"被头显驱动"。

7.1 安全上下文的三条路

方式做法适用限制
① HTTPS 托管
（推荐）		把 .html 与 three.min.js 放进任意 HTTPS 空间（本课程网站就是一份），得到一个短链接课堂演示、课后分享、给同学和家人看需要一个能放静态文件的空间
② 本地服务 + 端口转发在电脑上跑 python -m http.server 8080，头显通过 USB 端口转发访问 http://127.0.0.1:8080开发调试（改一次看一次）需要数据线、驱动与端口转发配置
③ 局域网 HTTP + 白名单浏览器打开 chrome://flags/#unsafely-treat-insecure-origin-as-secure，填入 http://192.168.x.x:端口，设为 Enabled 后重启浏览器应急（没有公网空间时）该开关随浏览器与固件版本变化，不一定存在；只适合临时使用
再强调一次：双击 file:// 打开，永远进不了 VR——它能看画面，但那只是"预览"，不是"运行"。判断方式很简单：如果按钮显示"当前浏览器不支持 WebXR"，先查安全上下文，再查设备。

7.2 在头显上打开场景：五步

  1. 确认两个文件在同一目录：主程序 .html 与 three.min.js（改名、移动都会导致加载失败）；
  2. 用方式①或②把它变成安全上下文；
  3. 在头显浏览器地址栏输入链接；
  4. 先看 HUD 上的统计面板有没有读数（FPS / DrawCalls）——有读数说明渲染正常，没有读数说明脚本报错了；
  5. 点"进入 VR"，戴好头显、确认手柄已连接，先原地环视一圈再尝试移动。

7.3 故障速查

现象最可能的原因处理
按钮显示"当前浏览器不支持 WebXR"不在安全上下文，或浏览器没有 WebXR换 HTTPS / localhost；确认浏览器版本
isSessionSupported 返回 false当前设备不支持沉浸式 VR 会话换浏览器或换设备；先在 PC 端把内容做完
会话启动失败，出现错误信息把设备不支持的能力写进了 requiredFeatures改成 optionalFeatures
进入 VR 后画面抖动 / 漂移代码在每帧改写相机姿态改为旋转玩家 rig（见 6.4）
页面空白three.min.js 路径错误或不在同目录；脚本报错开控制台看 404 与报错信息
画面很糊、明显掉帧像素比过高 / 阴影范围过大 / Draw Call 过多限制 setPixelRatio、收小阴影相机、做合批
画面看得见，但物体位置错乱把局部坐标当世界坐标使用（父容器没换算）合批或复制前先换算到世界坐标

上手成本较低，C# 语法友好，教学资料多较高，C++ 与蓝图双轨
XR 支持OpenXR + XR Interaction Toolkit，跨 PICO / Quest / Vive内置 XR 框架，偏向高保真与主机级画面

硬件接口 ①②：① 资产产出的模型有多“重”（面数、贴图），直接决定设备能不能跑满 90Hz；② 引擎越追求画面，越吃 GPU——生成设备（也就是“算力在哪”）不是抽象概念，它决定了你能选哪条技术路线。

资产从哪来：一个模型到 VR 的五道关

4.3 三条来路 + 五道关 + 三个最常翻车的坑

2.1 三条来路

素材库（最快）

Sketchfab 模型库、Poly Haven 贴图与 HDRI、Mixamo 角色动画。适合快速搭场景，注意授权与命名规范。

自己建（最可控）

用 Blender 从零建模，尺寸、拓扑、UV 自己说了算。代价是时间——课程里只在必要的小物件上使用。

AI 生成（最新）

Meshy、Hunyuan3D、TRELLIS 等文/图生 3D，适合快速原型。但要检查拓扑、UV、比例与版权，通常需要二次修整。

2.2 五道关：模型从建模软件到 VR 场景

① 建模  →  ② 减面  →  ③ 导出 FBX  →  ④ 导入设置  →  ⑤ 在场景里验证
            控制面数      禁中文路径      单位与缩放 ↑         戴上头显看
                                         最常翻车的一关
关卡要做什么没做好会怎样
① 建模按真实比例建模，统一单位进 Unity 后比例不对
② 减面控制在合理面数（一体机尤其敏感）掉帧、发热、眩晕
③ 导出 FBX路径与文件名不含中文导入失败、材质丢失
④ 导入设置检查 Scale / 轴向 / 材质模型躺倒、悬空、变成粉色
⑤ 验证先在模拟器看，再戴头显看“在 PC 上明明没问题”

2.3 最常见的三个坑

  1. 缩放不对：模型小到看不见、或大到撑爆场景 → 改 Transform → Scale（常用 1 或 0.01）；
  2. 贴图变粉红：材质丢失或路径含中文 → 重新指定材质，并把素材放到纯英文路径；
  3. 轴向搞错：模型躺倒或漂在空中 → Blender 默认 Z 轴向上，Unity 是 Y 轴向上，需要旋转或导出时校正。
硬件接口 ③：面数过高 → 掉帧 → 眩晕。这不是“画面问题”，而是接上了上次课的刷新率与 Motion-to-Photon 延迟：延迟一旦超标，人就会不适，再好的内容也救不回来。

检查项怎么做

位置是否合适调整 Transform → Position 的 Y 值（Unity 是 Y 轴向上）

C3 写出第一个脚本

Project 面板空白处右键 → Create → C# Script，命名为 SpinObject——首字母大写、不能有中文、不能有空格。

using UnityEngine;

public class SpinObject : MonoBehaviour
{
    public float speed = 60f;   // 每秒旋转的角度

    // Start 在物体第一次被激活时调用一次
    void Start()
    {
        Debug.Log("SpinObject 启动了");
    }

    // Update 每帧调用一次（适合做持续运动）
    void Update()
    {
        transform.Rotate(0f, speed * Time.deltaTime, 0f);
    }
}

挂载与运行

  1. 选中场景里的模型（或任意物体）；
  2. 把 SpinObject 从 Project 面板拖到 Inspector 下方空白处；
  3. 点 ▶ Play，物体开始旋转；
  4. Play 状态下可以在 Inspector 里实时改 Speed，看转速变化（试试从 60 改成 600）。

读代码要点（对应 4.3 开发语言）

概念在这个脚本里的体现
GameObject你挂脚本的那个物体
ComponentSpinObject 本身就是挂在物体上的一个组件
MonoBehaviourUnity 所有脚本的基类，必须继承
Start()只执行一次，适合初始化
Update()每帧执行，适合持续动作
Time.deltaTime让转动速度与帧率无关——快慢机器上转得一样
Time.deltaTime 是本课最值得记住的细节：没有它，高刷新率的机器上物体会转得更快。这和上次课讲的帧率、延迟是同一件事的两面。
